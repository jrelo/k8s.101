# PASSTHROUGH.md

A practical guide to passthrough mode in k8s.101 -- when to use it, when not
to, and what can still go wrong.

---

## What passthrough actually does

When you load a YAML file with passthrough enabled, the tool stores the entire
original parsed document in memory. On export it deep-clones that original,
then merges your form state on top of it field by field. Where fields overlap,
yours win. Where the original has fields the form knows nothing about, they
pass through untouched.

The merge is aware of containers specifically. Containers are matched by name,
so per-container unknowns (`startupProbe`, `securityContext`, `lifecycle`,
custom annotations on the container, etc.) survive alongside your changes.
A container you remove in the form gets dropped. A new one you add gets
appended. Pod-level unknowns (`initContainers`, pod `securityContext`,
`topologySpreadConstraints`, `nodeAffinity`, `tolerations`,
`terminationGracePeriodSeconds`, etc.) have always passed through safely.

---

## When to use it

**You loaded a file that was written by hand or by another tool, and you only
need to change something the form models.**

The clearest cases:

- Bump the image tag on a container that also has `startupProbe`,
  `securityContext`, and `lifecycle` configured by your platform team.
  Without passthrough those fields disappear. With it they survive.

- Change replicas or resource limits on a Deployment that has Vault agent
  injection annotations, Istio sidecar config, and ArgoCD sync-wave metadata.
  None of those are form fields. Passthrough keeps them.

- Add an environment variable to a container that already has `envFrom`
  referencing secrets you don't want to touch. The `envFrom` block passes
  through, your new `env` entry gets merged in.

- Edit a ConfigMap name or namespace and re-export without disturbing the
  twenty-line annotation block your CD tooling depends on.

---

## When not to use it

**You are authoring a new config from scratch.**

Passthrough requires a loaded document to merge against. If no file has been
loaded the checkbox still works but does nothing -- the output is just the
form state. There is no risk here, it just has no effect.

**The original file has structural patterns the parser cannot round-trip.**

The tool uses a hand-rolled YAML parser. If the original file uses multi-line
block scalars (`|`, `>`), anchors and aliases (`&anchor`, `*alias`), or inline
nested mappings (`{key: val}`), the parsed object may not match the original
faithfully. Passthrough will re-serialize that degraded object, potentially
losing or mangling content you expected to preserve. Check the raw editor
after loading -- if the YAML looks different from what you loaded, do not
rely on passthrough for that file.

**The file was generated by Helm or Kustomize with templating artifacts.**

Helm chart output sometimes contains comments, custom tags, or formatting
conventions that do not survive the parse/serialize round-trip even when the
YAML is technically valid. The output will be functionally equivalent but
will look different enough to cause noisy diffs or confuse downstream tooling
that parses comments.

**You need to make changes to per-container fields the form does model, AND
the original container has a different value for those fields you want to keep.**

Example: the original has `imagePullPolicy: Always`. You load the file, do not
touch the pull policy field (it reads `IfNotPresent` from form defaults because
the mapper fell back to a default). You export. The form value wins -- `Always`
is now `IfNotPresent`. Passthrough does not protect you from fields the form
knows about and overwrites with its own value. Check the output diff before
applying.

## Pitfalls in practice

**The form always wins on fields it models, even if you did not touch them.**

This is the most common surprise. You load a file to change one thing. The
mapper pulls values from the file where it can, but any field it does not
recognize or maps imperfectly gets set to a form default. On export, that
default overwrites the original value. Specific fields to watch:

- `imagePullPolicy` -- defaults to `IfNotPresent`. If your original was
  `Always` and the container image has no tag or uses `:latest`, this is
  a real operational difference.
- `maxUnavailable` in rolling update -- defaults to `25%`. If your original
  had `0` for zero-downtime rolling, the form will revert it.
- `dnsPolicy` -- defaults to `ClusterFirst`. Usually fine but not always.
- Probe `periodSeconds` and `failureThreshold` -- the form only exposes
  `initialDelaySeconds`. Other probe fields are hardcoded in the generator.
  If your original had `failureThreshold: 1` on a liveness probe for fast
  failure detection, the export will reset it to the form default of `3`.

**Renamed containers break the match.**

The container merge works by matching on `name`. If you rename a container
in the form (e.g. from `api` to `web`), the tool sees a new container named
`web` and a removed container named `api`. The original `api` container's
unknowns are dropped, and `web` is a clean slate. If the rename is intentional
that is correct behavior. If it was accidental it is a silent data loss.

**The raw editor and passthrough interact in a specific order.**

If you open the raw editor, make changes, and hit apply -- the tool re-parses
your raw YAML and updates form state. It also updates `passthroughDoc` to your
edited version. This is intentional: the raw editor is the escape hatch for
things the form cannot express, and your raw edits should be treated as the
new baseline for subsequent form edits. What this means in practice: if you
add a `startupProbe` directly in the raw editor and then change replicas in
the form, your raw-editor-added `startupProbe` will survive because it is now
part of the passthrough baseline.

**Multi-document files are not supported for export.**

If you load a file that contains multiple documents (Deployment + Service +
ConfigMap all in one file separated by `---`), only the first recognized
resource kind is loaded into the form. The others are silently ignored.
Passthrough only covers the one document that was loaded. Do not load
multi-document files expecting to re-export the whole stack.

**Serialization style changes will appear as diffs in git.**

Even when passthrough preserves all the right values, the re-serialized output
may look different from the original: different quote styles, different key
ordering within mappings, block scalars replaced with quoted strings, comments
stripped. The YAML is semantically equivalent but `git diff` will show changes
on lines you did not intend to touch. If your repo has CI that diffs applied
manifests against stored ones, expect noise. Run `validate-yaml.py` to confirm
the content is correct, but accept that the formatting will not be identical
to the original.

---

## The safe workflow for high-stakes edits

1. Load the file. Enable passthrough.
2. Check the raw editor immediately. Does the loaded YAML look faithful to the
   original? If not, stop and edit the file directly in your editor.
3. Make your change in the form.
4. Before exporting, check the output pane. Diff it mentally against what you
   expect. Look specifically at the fields listed above that the form overwrites
   with defaults.
5. Export. Run `python3 validate-yaml.py <file.yaml>`.
6. Do a `kubectl diff -f <file.yaml>` against your cluster before applying
   if the deployment has any production traffic.
